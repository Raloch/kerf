# Kerf

浏览器里的视频剪辑器，**导出全程在客户端完成**——素材不上传，不需要转码服务器。

> 状态：开发中。剪辑、创作、导出的闭环都通了——多轨时间轴、文字、关键帧动画、转场、调色、LUT、音量包络、音频波形、多项目与首页都能用，长片（30 分钟）在桌面和手机上都实测导出通过。**变速**也做完了（画面 + 声音 + 界面；声音走重采样所以会变调，界面上有提示）。**保音高**也做完了：检查器里可以在"跟着变调（重采样）"和"保持音高（时间伸缩）"之间选，端到端护栏是"2× 之后提示音仍是 1kHz，而只差那个开关的对照段是 2kHz"。片段的**复制 / 粘贴 / 副本**（⌘C / ⌘V / ⌘D）和**多选**（⌘ 点选 / ⌘A / Esc / 框选，整组拖拽、批量删除粘贴都是一条撤销）也能用了。

*kerf* 是锯片切过木料留下的那道缝。剪辑软件里最核心的动作就是这一刀。

---

## 现在能做什么

一条完整的剪辑链路，全程在浏览器里：

```
导入素材 → 多轨时间轴（拖拽/裁切/切分/磁吸/撤销） → 预览（带声音） → 导出 MP4 / WebM
   ↑                    ↑                                              ↑
视频·音频·图片      文字·关键帧·转场·调色·LUT          解码 → 合成 → 编码 → 封装 → 流式写盘
                                                    WebCodecs + WebGL，跑在 Web Worker 里
```

**素材**三种：带画面的视频、**纯音频**（配乐 / 旁白）、**图片**。导入是"追加"不是"载入"，所以可以先剪画面再配音乐。视频会在后台自动转 720p 代理存进 OPFS（预览拖播放头才跟得上手），**导出始终读原片**。

**时间轴**多轨、片段永不重叠、磁吸（拖拽时按 ⌥ 临时关闭）、⌘K 切分、⌘Z 撤销（连续拖拽合并成一步）。片段上画缩略图和音频波形；选中片段的每个有动画的属性在时间轴上各展开一行，钻石可以横向拖动改时间。

**创作能力**：

| | |
|---|---|
| 文字 | 自动断行（`Intl.Segmenter` 按字素簇，避头尾）、描边、阴影（颜色带透明度）、**自定义字体**（`.ttf/.otf/.woff2`） |
| 动画 | 变换六项 + 调色五项 + 音量共 12 个属性可打关键帧，命名缓动 |
| 转场 | 交叉溶解、擦除、圆形张开、推移、故障；音频侧等功率 / 等增益淡化 |
| 调色 | 一级调色（亮度/对比度/饱和度/色相）+ **3D LUT**（`.cube`） |
| 音频 | 多轨混流、片段音量、音量包络（关键帧）、交叉淡化 |

**预览会出声**，而且播的是导出会写进成片的那份 PCM——不是另混一遍（见下面「几个刻意的技术选择」）。

**导出**按整份 EDL 走：多个片段分别指向不同源片、轨道空档产黑帧、多轨音频分段混流后编码，成品边编码边写盘（不在内存里攒 Blob）。Chrome / Edge 走系统保存对话框直写文件；Safari / Firefox 回退成先写 OPFS 再触发下载。

**编辑成果自动落盘**（IndexedDB，防抖 1 秒 + 转入后台立刻冲），标签页被杀之后打开能接着编。素材存的是磁盘引用而不是拷贝，所以文件被移走时会明确报出丢了哪个、影响几个片段。

## 实测数字

性能数字**必须带机器**，不带的跨机器比较会得出错误结论。历次测量记在 [docs/PLAN.md](docs/PLAN.md) §4 的基线表里，**只追加不改旧行**——旧行的价值就是当对照。

| 场景 | 机器 | 结果 |
|---|---|---|
| 1080p30 · 60 秒 · H.264+AAC | Apple M3 Max / Chrome 150 | 5.0–5.4 秒 = **11–12× 实时** |
| 1080p30 · **30 分钟**（53946 帧） | Apple M3 Max / Chrome 150 | 169.9 秒 = **10.59× 实时** · 成片 281 MB |
| 720p · 30 分钟（54000 帧） | Apple M3 Max / Chrome 150 | **13.5× 实时** |
| 720p · 30 分钟（54000 帧） | Apple M3 Max / Safari 26.5 | **4.4× 实时** |
| 720p · 30 分钟（54000 帧） | iPhone / iOS Safari | **7.36× 实时** · 244.7 秒 |

内存是长片唯一真正的墙，所以**自己记账**（不问浏览器，理由见下）：

- **混音峰值在 60 倍片长上一个字节都没动**：5.7 MB @ 30 秒 = 5.7 MB @ 30 分钟。分段混流之前是 989 MB（30 分钟）。
- **导出循环峰值完全平**：1080p 30 分钟从第 9 帧起 659 → 665 → 662 MB，65 分钟长的循环里解码帧恒定 5.9 MB。
- 每次导出跑完 `leaked*` 必须全是 0。泄漏在几百帧的自检片上完全看不出来，到 30 分钟才会变成标签页崩掉。

手机上**"墙"一道都不存在**：片长（四档全过）、导出次数（一页 24 次连导全过、吞吐死平）、跨档累积（整条阶梯一页跑完四档全过）——先后立过三道，全部倒了。曾经判出的三道墙都是**量法的 bug**，经过记在 §8 风险 4。

首屏主 chunk **362 kB（gzip 119 kB）**：mediabunny（约 500 kB）只出现在 Worker 里或被动态 `import()`，PixiJS 靠一个**异步工厂**隔离（对 `pixi.js` 只有 `import type`，实例走函数里的动态 `import()`），两者都不进主 chunk。这个坑踩过两次，所以现在**构建自己会拦**：判据是入口 chunk 的**模块图**，不是字节上限也不是在产物里搜包名——后者是一条恒为真的假断言（`grep -c mediabunny` 在真的就是 mediabunny 的那个 chunk 上也返回 0，压缩把包名丢光了）。理由见 PLAN.md 的 **D38**。

## 快速开始

```bash
pnpm install
pnpm dev
```

打开页面就是编辑器。不需要准备视频文件——顶栏「M0 自检」里可以一键合成测试素材。

其他命令：

```bash
pnpm test         # 单元测试，988 项 / 33 个文件
pnpm typecheck    # 类型检查（strict + noUncheckedIndexedAccess + exactOptionalPropertyTypes）
pnpm build        # 生产构建（自带主 chunk 断言）
pnpm gate         # 上面三条一起跑，CI 上跑的就是它
pnpm dev:device   # 真机自检用：监听局域网 + 自签 HTTPS
```

`pnpm gate` 绿**不等于成片是对的**：它覆盖不到下面那六个跑在真实浏览器里的自检，而这个仓库里几乎每一个真 bug 都是那些抓到的。

`pnpm dev:device` 要自签 HTTPS 是因为 **WebCodecs 和 OPFS 都要求安全上下文**，`localhost` 算、`http://192.168.x.x` 不算。直接开局域网地址会得到"没有 VideoEncoder"，看起来像"这台设备不支持"——这个坑真机上踩过一次。

## 六个自检

有几类错误**不会报错，只会静默产出错误的片子**——帧数少一帧、trim 起点偏一帧、跨片段边界读错源片位置、预览和导出画面不一致、音画偏移 44 ms、成片里少一层画面。单元测试覆盖不到这些，所以有一批跑在**真实浏览器**里的自检（顶栏「M0 自检」进）。

前四个进回归门禁，改到相关地方就得跑：

| 自检 | 断言数 | 在验什么 |
|---|---|---|
| M0 自检 | 72 | 生成素材 → 探测 → 导出 trim 区间 → 读回断言。含音频交叉淡化、分段混音逐样本对拍、片段音量、**预览听到的 == 成片里的**（AudioWorklet 抓预览输出，实测最大差 3.02e-16）、纯音频素材落点 |
| 预览 / 导出一致性 | 23 | 同一帧分别走预览和导出，逐像素比对；含关键帧摆位、文字层、调色、LUT、图片层 |
| 多片段一致性 | 54 | 四片段 + 空档 + 交叉溶解整条导出后比对 13 个取样帧；转场断言是**成对的**（一致性 + 混合比例） |
| PixiJS 后端 | 31 | Worker 里起 WebGL2，与 Canvas2D 跑同一份输入比对；含上下文丢失与恢复、上下文预算、GPU-vs-CPU 参照实现（调色 / LUT / shader 转场） |

后两个**不进门禁**：真机自检（分辨率轴）和长片自检（长度轴）。前四个问"代码对不对"，答案在所有机器上都该一样；这两个问**这台设备的上限在哪**，答案本来就因机而异。

跑自检不用手点也不用截图：URL 上加 `?autorun=m0`（或 `pixi` / `timeline` / `preview` / `device` / `length` / `clear`）会自动跑完并把**完整结果**POST 到 `.reports/`。

几条从踩坑里长出来的判据：

- **中间两个刻意用方形输出跑**，这样 16:9 素材必然产生上下黑边——黑边高度差一个像素就说明两条渲染路径的缩放算法已经分叉。
- 多片段自检能断言"这一帧取到的确实是源片第 N 帧"：测试素材的背景色相随帧号线性渐变，所以**色相编码了源片帧号**。时间轴第 80 帧应该显示源片第 200 帧（色相 200°），取帧游标没在片段边界切换的话会显示 60°——差 140°，任何容差都盖不住。
- **"两条路径比对"覆盖不了渲染算法本身。** 把 shader 写错时预览/导出一致性自检是**绿的**——两条路径共用同一个（错的）shader。所以每加一种 GPU 效果都要同时加一份能在 JS 里跑的参照实现，由第四个自检拿它和 GPU 对拍。
- **反向验证是必须的**：断言写完要故意破坏被测代码，确认它真的会红、而且红的是你以为的那一条。做过好几次"注入了却没红"——有时是断言没牙，**有时是注入的东西根本不改变行为**，两者不能默认前者。

## 浏览器要求

客户端导出依赖 WebCodecs，这是硬门槛：

| 浏览器 | 导出 MP4（H.264 + AAC） | 导出 WebM（VP9 + Opus） |
|---|---|---|
| Chrome / Edge 94+ | ✅ | ✅ |
| Safari 26+（含 iOS） | ✅ | ✅ |
| Firefox 130+ 桌面 | ❌ 不能编码 AAC | ✅ |
| Linux 桌面浏览器 | ❌ 不能编码 AAC | ✅ |
| Firefox Android | ❌ | ❌ |

缺少 AAC 编码能力时，界面会禁用 MP4 并就地说明原因，**不会静默换成别的格式**——用户点了 MP4 却拿到 WebM 是最糟的体验。

导出面板另有一层**环境体检**，把派生现象折叠回根因：非安全上下文里 `VideoEncoder` 根本不存在，于是四个编码全报"不可用"——那时只报"页面不是安全上下文"这一条，并且出路指向换 scheme 而不是"换浏览器"。估算出来的结论（比如空间可能不够）只提醒不阻断：预测偏大时阻断掉的是一次本来能成的导出。

还会量出**这台机器真实的导出吞吐**，据此预测这次要跑多久；慢于实时到一定程度就提醒，但**不封顶分辨率**——静默把 4K 换成 1080p 就是"选了 A 拿到 B"，而按设备分档（UA / 核数）测的不是被测对象。

一处能力缺口值得单独记：**Safari 没有 `showSaveFilePicker`**（实测 26.5.2），所以那边成品**只可能**走"流式写 OPFS 再触发下载"这条回退路。这意味着凡是"写盘路径上的结论"，都只对没有 picker 的浏览器有实测依据。

## 几个刻意的技术选择

**预览和导出共用同一个 `compose(edl, frame)`，也共用同一套取帧决策。** 不允许存在两套渲染路径——这是"预览和导出画面不一致"的唯一根因。共用合成器只保证"画法一致"，所以"该画哪个片段、按什么顺序、读源片哪一刻"也收在同一个模块里（`edl/sampling.ts`）。

**预览出声播的是导出那份 PCM，不是自己再混一遍。** 跑同一个 `createMixer`、把产出的段排进实时 `AudioContext`，所以淡化曲线、等功率还是等增益、静音轨处理**不可能分叉**——上面那条硬规则在音频上的护栏比画面更强：不是共用算法，而是**根本没有第二份实现**。

**帧 → 源片位置要过一次时间，不能做帧号加减。** `sourceIn + (帧 - timelineIn)` 隐含假设源片帧率等于时间轴帧率；把 25fps 素材放到 30fps 时间轴上，成片会慢 20% 且不报任何错。

**时间一律用有理数帧号，不用浮点秒。** 29.97fps 实际是 30000/1001，用浮点近似做帧运算会累积误差；实测用 `round(fps)` 代替有理数，10 分钟内就错位 18 帧。浮点秒只允许出现在调用底层库的那一行。

**导出取帧用 `VideoDecoder` 顺序解码，不用 `video.currentTime`。** 后者不帧精确，而且锁死在 1× 实时速度，做不了导出。

**每加一种 GPU 效果，都要同时加一份能在 JS 里跑的参照实现。** 调色编译成一个 5×4 色彩矩阵、LUT 查表、转场混合函数各有一份 CPU 实现，GLSL 与它们逐行对应。这样"shader 有没有按那个算法算"才有判据——单元测试够不着，两条路径比对也覆盖不了。为此故障转场的伪随机换成了 **PCG 整数哈希**（只有 mod 2³² 的乘法、移位、异或），因为 `fract(sin(x)*43758.5453)` 在 GPU 和 JS 上不逐位相同，会让那条断言松到抓不住东西。

**内存要自己数，不要问浏览器。** `measureUserAgentSpecificMemory()` 需要 COOP/COEP（那套头会打断页面里的第三方脚本），而 `performance.memory` **只报 JS 堆**——导出的内存几乎全不在 JS 堆上（解码帧、画布后备存储、解码器缓冲都不算），一条长片能把显存吃光而那个数几乎不动。所以在借出/归还处各记一笔，记账点**贴着 `close()` 写**。

**导出结果流式写盘，不攒成 Blob。** 1080p 按 8Mbps 算是 60MB/分钟，十分钟就 600MB 全在堆里，而且封装完成前一个字节都写不出去——中途失败等于白跑。

**音频混流在主线程，不在 Worker。** `OfflineAudioContext` 在 Worker 里不可用。混音本身只是相加，难的是重采样和声道上混（素材 44.1k/48k、单声道/立体声混着来），把每个片段挂成 `AudioBufferSourceNode` 交给音频图，比自己写重采样可靠得多。混好的 PCM 用 transfer 交进 Worker，不靠结构化克隆——几百 MB 会整份复制一遍。

**混音按段产出，而且必须是"拉"不能是"推"。** 整条混完的峰值随片长线性涨（30 分钟 989MB）；分段之后峰值与片长无关。推的话主线程会尽快把所有段发过去，Worker 那边照样堆成整条 PCM，一个字节都没省。

**不把 ffmpeg.wasm 放主路径。** 软编慢 10–50 倍，多线程版需要 COOP/COEP 响应头，会打断页面内的第三方脚本和跨域 iframe。

**导出侧复用常驻合成器。** WebGL 上下文有预算，超了浏览器驱逐**最老的那个**——所以危险的不是新建的，是**预览**（它从打开项目起就一直握着一个）。Safari 上实测：每轮新建时 12 轮就把预览的上下文驱逐掉，而且**救不回来**（被预算驱逐的上下文 `recover()` 会超时，浏览器要等预算腾出来才还）。iOS 上同一组对照给出同样结论，所以复用常驻合成器不是优化而是唯一解。

技术栈：[mediabunny](https://mediabunny.dev/)（编解码与封装）· PixiJS v8（合成，锁 WebGL2 不用 WebGPU）· React + Vite · Zustand + Immer。选型理由和评估过但没选的方案见 [docs/PLAN.md](docs/PLAN.md)。
