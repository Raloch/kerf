# Kerf

浏览器里的视频剪辑器，**导出全程在客户端完成**——素材不上传，不需要转码服务器。

> 状态：开发中。剪辑与导出的闭环已经通了——导入、多轨时间轴、拖拽裁切、预览、导出成片都能用。创作能力（文字、关键帧、转场、滤镜）还没做。

*kerf* 是锯片切过木料留下的那道缝。剪辑软件里最核心的动作就是这一刀。

---

## 现在能做什么

一条完整的剪辑链路，全程在浏览器里：

```
导入素材 → 多轨时间轴（拖拽/裁切/切分/磁吸/撤销） → 预览播放 → 导出 MP4 / WebM
                                                          ↑
                              解码 → 合成 → 编码 → 封装 → 流式写盘
                              WebCodecs 硬件加速，跑在 Web Worker 里
```

具体来说：

- **导入**后台自动转 720p 代理存进 OPFS（预览拖播放头才跟得上手），并抽缩略图铺到片段上。**导出始终读原片**，代理不影响成片画质。
- **时间轴**多轨、片段永不重叠、磁吸（拖拽时按 ⌥ 临时关闭）、⌘K 切分、⌘Z 撤销（连续拖拽合并成一步）。
- **导出**按整份 EDL 走：多个片段分别指向不同源片、轨道空档产黑帧、多轨音频混流后编码，成品边编码边写盘（不在内存里攒 Blob）。Chrome / Edge 走系统保存对话框直写文件；Safari / Firefox 回退成先写浏览器存储再触发下载。

实测约 **12–13× 实时**（640×360，H.264 硬编）。

界面按 **[这份可交互设计稿](https://raloch.github.io/kerf/)** 实现（源文件 [design/kerf-editor-mockup.html](design/kerf-editor-mockup.html)，单文件零依赖，clone 后双击也能打开）。

## 快速开始

```bash
pnpm install
pnpm dev
```

打开页面就是编辑器。不需要准备视频文件——顶栏「M0 自检」里可以一键合成测试素材。

其他命令：

```bash
pnpm test         # 单元测试，115 项（时间基 / 状态层 / 取样映射 / 导出预设）
pnpm typecheck    # 类型检查（strict + noUncheckedIndexedAccess + exactOptionalPropertyTypes）
pnpm build        # 生产构建
```

## 四个自检

有几类错误**不会报错，只会静默产出错误的片子**——帧数少一帧、trim 起点偏一帧、跨片段边界读错源片位置、预览和导出画面不一致。单元测试覆盖不到这些，所以有几个跑在真实浏览器里的自检（顶栏「M0 自检」进）：

| 自检 | 断言数 | 在验什么 |
|---|---|---|
| M0 自检 | 16 | 生成素材 → 探测 → 导出 trim 区间 → 读回断言帧数/时长/帧率/音轨/首帧时间戳归零 |
| 预览 / 导出一致性 | 5 | 同一帧分别走预览（`video` seek）和导出（`VideoDecoder` 顺序解码），逐像素比对 |
| 多片段一致性 | 23 | 两个片段 + 中间空档整条导出，比对 7 个取样帧 |
| PixiJS 后端 spike | 11 | 在 Worker 里起 WebGL2，与 Canvas2D 后端跑同一份输入比对 |

中间两个刻意用**方形输出**跑，这样 16:9 素材必然产生上下黑边——黑边位置差一个像素就说明两条渲染路径的缩放算法已经分叉。

多片段自检还能断言"这一帧取到的确实是源片第 N 帧"：测试素材的背景色相随帧号线性渐变，所以色相编码了源片帧号。时间轴第 80 帧应该显示源片第 200 帧（色相 200°），如果取帧游标没在片段边界切换，它会显示源片第 60 帧（60°）——差 140°，任何容差都盖不住。

第四个不是回归自检，是**换渲染后端之前必须成立的前提**，所以它跑在写 M2 功能代码之前而不是之后。除了比对两个后端的画面，它还主动制造两个只有 WebGL 才有的失效模式：跨 task 后 drawing buffer 被清空，以及 GL 上下文丢失——后者在导出跑几分钟时会被切标签页或系统休眠触发，默认行为是渲染静默变成 no-op。

## 浏览器要求

客户端导出依赖 WebCodecs，这是硬门槛：

| 浏览器 | 导出 MP4（H.264 + AAC） | 导出 WebM（VP9 + Opus） |
|---|---|---|
| Chrome / Edge 94+ | ✅ | ✅ |
| Safari 26+ | ✅ | ✅ |
| Firefox 130+ 桌面 | ❌ 不能编码 AAC | ✅ |
| Linux 桌面浏览器 | ❌ 不能编码 AAC | ✅ |
| Firefox Android | ❌ | ❌ |

缺少 AAC 编码能力时，界面会禁用 MP4 并就地说明原因，**不会静默换成别的格式**——用户点了 MP4 却拿到 WebM 是最糟的体验。

## 项目结构

```
src/
├─ time/        有理数帧号 ↔ 微秒 ↔ 时间码
├─ edl/         EDL 类型 + 取样映射（预览与导出共用的取帧决策）
├─ state/       编辑操作（纯函数）、撤销栈、Zustand store
├─ media/       能力探测、素材探针、OPFS 代理转码、缩略图
├─ compose/     合成层，生产路径是 Canvas2D；PixiJS 后端已备好但尚未接入
├─ audio/       多轨混流（主线程，OfflineAudioContext）
├─ export/      导出流水线 + 取帧游标 + Worker + 流式写盘 + 预设
├─ preview/     预览引擎（seek + rAF 采样）
├─ ui/          编辑器四区布局、时间轴、导出面板
└─ dev/         测试素材生成 + 三个自检脚本
design/         界面设计稿
docs/PLAN.md    技术方案（活文档）
```

## 几个刻意的技术选择

**预览和导出共用同一个 `compose(edl, frame)`，也共用同一套取帧决策。** 不允许存在两套渲染路径——这是"预览和导出画面不一致"的唯一根因。共用合成器只保证"画法一致"，所以"该画哪个片段、按什么顺序、读源片哪一刻"也收在同一个模块里（`edl/sampling.ts`）。

**帧 → 源片位置要过一次时间，不能做帧号加减。** `sourceIn + (帧 - timelineIn)` 隐含假设源片帧率等于时间轴帧率；把 25fps 素材放到 30fps 时间轴上，成片会慢 20% 且不报任何错。

**时间一律用有理数帧号，不用浮点秒。** 29.97fps 实际是 30000/1001，用浮点近似做帧运算会累积误差；实测用 `round(fps)` 代替有理数，10 分钟内就错位 18 帧。浮点秒只允许出现在调用底层库的那一行。

**导出取帧用 `VideoDecoder` 顺序解码，不用 `video.currentTime`。** 后者不帧精确，而且锁死在 1× 实时速度，做不了导出。

**不把 ffmpeg.wasm 放主路径。** 软编慢 10–50 倍，多线程版需要 COOP/COEP 响应头，会打断页面内的第三方脚本和跨域 iframe。

**导出结果流式写盘，不攒成 Blob。** 1080p 按 8Mbps 算是 60MB/分钟，十分钟就 600MB 全在堆里，而且封装完成前一个字节都写不出去——中途失败等于白跑。

**音频混流在主线程，不在 Worker。** `OfflineAudioContext` 在 Worker 里不可用。混音本身只是相加，难的是重采样和声道上混（素材 44.1k/48k、单声道/立体声混着来），把每个片段挂成 `AudioBufferSourceNode` 交给音频图，比自己写重采样可靠得多。

**换渲染后端之前先把风险验掉，而不是等功能写完。** M2 的滤镜要 GPU，但合成器同时被预览（主线程）和导出（Worker）依赖，而 Pixi 在 Worker 里能不能跑是个会波及接口设计的结论。所以先落了一个可互换的 PixiJS 后端和 11 项前提断言，暂不接入——同时换渲染层和加图层类型，画面一旦不对就分不清是关键帧算错了还是纹理上传错了。

技术栈：[mediabunny](https://mediabunny.dev/)（编解码与封装）· PixiJS v8（合成，M2 后半段接入）· React + Vite · Zustand + Immer。选型理由和评估过但没选的方案见 [docs/PLAN.md](docs/PLAN.md)。
