# Kerf 技术方案

Web 视频剪辑器，**导出在客户端完成**。服务端导出不在本方案范围内。

- 最后更新：2026-07-25
- 界面设计稿：[design/kerf-editor-mockup.html](../design/kerf-editor-mockup.html)（单文件、零依赖，双击可开）
- 在线版：https://claude.ai/code/artifact/244a2705-452c-4774-ac2c-2909b4096401
- 当前阶段：**M1 已完成**（编辑器骨架可用：导入、多轨时间轴、拖拽裁切磁吸、预览播放、代理与缩略图）。下一步 M2 创作能力

---

## 1. 核心判断

不存在"一个库搞定全部"。真正的分水岭是**导出路径**，客户端导出在 2026 年只有一个正解：**WebCodecs 硬件编解码 + JS 封装器**。上层的合成、时间轴、UI 都围绕这条管道搭建。

三条可选导出路径，以及为什么只选一条：

| 路径 | 特点 | 结论 |
|---|---|---|
| `MediaRecorder` + `canvas.captureStream()` | 五行代码出片，但只能实时录制（锁 1x）、会丢帧、质量不可控 | **仅 M0 做对照基准**，验证完丢弃 |
| **WebCodecs + mediabunny** | 硬件加速，可超实时，帧精确 | **主路径** |
| ffmpeg.wasm | 纯软编，慢 10–50×；多线程版需 COOP/COEP 响应头，会打断页面内第三方脚本和跨域 iframe | **不进主路径**，仅在需要补 AAC 时考虑 libav.js |

## 2. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 编解码 + 封装 | **mediabunny** | mp4-muxer / webm-muxer 作者的继任项目，纯 TS 零依赖，demux/mux/转码全包，可注册自定义编码器做 fallback。MPL-2.0，可闭源商用。Remotion 官方也已把编码层切到它 |
| 画面合成 | **PixiJS v8**（WebGPU → WebGL 自动降级） | 转场、混合模式、LUT、色键、遮罩必须上 GPU；Pixi 的 filter / renderTexture 体系省掉大半自研量 |
| 音频混流 | **OfflineAudioContext**（浏览器原生） | 唯一能超实时离线混音的方案，直接出 PCM |
| 时间轴 UI | **自研**（虚拟化 + transform 定位） | 现有 React 时间轴库撑不住多轨 + 磁吸 + 帧级缩放，改造成本高于自研 |
| 状态管理 | **Zustand + Immer** + 自研 undo 栈（命令模式） | EDL 需要不可变快照才能做撤销，以及保证"预览 = 导出" |
| 大文件存储 | **OPFS** + File System Access API | 源片、代理文件、导出结果都不能进内存 |
| 兜底编码 | libav.js（可选，仅补 AAC） | 见 §5 兼容性 |

### 评估过但没选

- **Rendley SDK**（商业授权）— 文档完整、转场/动画字幕开箱即用，适合"要交付产品"而非"要建能力"。如果工期压力大于可控性可以回头考虑。
- **Diffusion Studio core** — 设计目标契合，但 npm / GitHub 上存在多个不同来源的 fork（`msabansal`、`chebum`、`snack-dev`、`@diffusionstudio/core-v2`），**原仓库维护状态和许可需要自己确认清楚再押注**。
- **Remotion** — 更适合"程序化生成 / 模板批量出片"而非"用户拖时间轴剪辑"。其 `@remotion/web-renderer` 客户端渲染仍标注 experimental，且官方正在把编码层从自家 `@remotion/webcodecs` 迁到 mediabunny，押它要接受 breaking change。

## 3. 架构主干：一个函数同时驱动预览和导出

这是整个项目最重要的一条设计约束。绝大多数自研剪辑器最后崩在"预览和导出画面不一致"上。

```
EDL（不可变 JSON：tracks / clips / effects / transitions）
        │
        ▼
compose(edl, frameIndex) ──► VideoFrame        ← 唯一的合成入口
        │                          │
   预览：requestAnimationFrame     导出：顺序驱动，不依赖墙上时钟
   （丢帧无所谓）                  （每帧必渲染，帧精确）
```

预览和导出只有两处差异：**帧来源**和**节奏控制**。

- **预览取帧**：`HTMLVideoElement` seek（便宜、够用），配合低码率**代理文件**（导入时后台转 480p/720p，用 mediabunny 转码写进 OPFS）
- **导出取帧**：**必须**用 `VideoDecoder` 顺序解码。`video.currentTime` 不帧精确，且锁在 1x 实时速度，做不了导出

## 4. 导出流水线

```
        ┌─ VideoDecoder（从关键帧开始顺序解码，帧缓存 ~30 帧）
源片 ──►│
        └─ 音频 packets ──► OfflineAudioContext 离线混音 ──► PCM
                │
   compose() 逐帧合成 ──► VideoFrame ──► VideoEncoder ─┐
                                                      ├─► mediabunny Output（mp4）
                        PCM ──► AudioData ──► AudioEncoder ─┘
                                                            │
                                              StreamTarget ──► OPFS / showSaveFilePicker
```

### 必须一开始就做对的六件事

1. **`VideoFrame` 是 GPU 资源，忘记 `.close()` 会在几秒内 OOM。** 所有帧对象走"借出—归还"池化管理，不要靠 GC。
2. **背压控制**：`encoder.encodeQueueSize > 10` 就暂停投喂，否则编码器队列爆掉。
3. **时间基统一**：内部一律用微秒时间戳 + 有理数帧号（`num/den`），**永远不要用浮点秒做帧计算**——29.97fps 的累积误差会让 10 分钟视频音画错位几帧。
4. **GOP 边界**：clip 起点几乎不在关键帧上，解码必须回退到前一个 keyframe 再丢弃多余帧。这块逻辑不写对，trim 就会花屏。
5. **解码 / 合成 / 编码全部放 Web Worker**，`VideoFrame` 可 transfer 过去零拷贝；主线程只跑 UI，否则导出期间界面完全卡死。
6. **导出结果流式写盘**，不要攒成一个 Blob。

### M0 实施中发现的四件事

这些是写代码时才暴露出来的，方案阶段想不到：

1. **帧对齐必须带微秒级容差。** 帧号换算成秒会做微秒取整（偏差 ≤0.5μs），而解码器给出的 `sample.timestamp` 是未取整真值。两者直接比较会把"恰好等于"判成"还没到"，导致每个 trim 区间**末帧少一帧**——导出状态、帧数、时长全部正常，只有把文件读回来看画面才发现。现为 `FRAME_ALIGN_EPSILON_SECONDS = 1e-6`，并有单元测试锁死（`timebase.test.ts` 的"帧对齐容差"一节）。凡是拿"算出来的秒"与"解码器给的秒"比较，都要带这个容差。
2. **时间轴时长必须按视频轨算，不能用容器总时长。** AAC 编码器会在音轨头尾加 priming/padding，音轨通常比视频轨长几帧；用 `input.computeDuration()` 会把 300 帧的素材算成 303 帧，末尾多出空档。要用 `videoTrack.computeDuration()`，且换算用 `round` 而非 `ceil`。
3. **`OfflineAudioContext` 在 Worker 里不可用**（Web Audio 不暴露给 Worker）。M0 是单音轨，走 `AudioSampleSink → AudioSampleSource` 转封装即可，整条管道都留在 Worker 里。**M2 做多轨混音时，PCM 必须在主线程用 OfflineAudioContext 算好，再 transfer 进 Worker** —— 这会改变导出流水线的形状，届时要重新设计 Worker 协议。
4. **mediabunny 的 `await source.add()` 本身就是背压**。它的 Promise 在编码器就绪时才 resolve，await 它等价于给编码队列施加背压，不需要自己轮询 `encodeQueueSize`。硬规则 5 因此简化为"必须 await add()"。

### 性能基线（只追加，不改旧行）

数字**不来自专门的压测脚本**，来自导出面板自己报的那一行（完成后显示 `N.N 秒（M.M× 实时）`）。所以任何人在任何机器上正常导出一次就能补一行，不需要额外工具——把测量塞进已经会跑的路径，才不会随时间烂掉。

记录规则：

- **只追加，不修改旧行。** 旧行的价值就是当对照，改掉等于把对照删了。
- **必须写机器和配置。** 不带机器的倍速数字没有意义，跨机器比较会得出错误结论。
- 大改合成层前后各记一行（M2 就是这样一个节点）。

最后一行比第二行还快，进一步说明这几行的差别都在噪声里——这套测法是"跑一次、报一个数"，不取中位数，4–8% 的浮动区分不出真实变化。**注意最后一行的时间轴没有文字层**，所以它量的是"加了文字能力之后，不用文字的项目有没有变慢"，不是文字渲染本身的成本。文字的成本要另外记：栅格化按 (文案 + 样式 + 输出尺寸) 缓存，一个片段整个时长只排版一次，逐帧只是一次 `drawImage`。

后几行与第二行的差别是**噪声**，不是回归：三次的字节数完全相同（11,410,343），而这两步都没进逐帧热路径的深处——第 1 步只多了一次 `kind` 判断，第 2 步多了一次 `isDefaultGeometry()` 判断且恒等时仍走原来的 `drawImage`。这几行的作用是"下一步出问题时有个紧邻的对照"，不是"证明这一步没变慢"：4% 的差在这套测法（一次导出、不取中位数）下区分不出来。

最后一行的字节数与前几行差 0.3%（11,446,640 / 11,410,343）：它不是从导出面板点的，而是在控制台直接调 `startExport`，音频码率等参数是手填的，与预设解析出来的未必逐位相同。跨行比时间可以，比字节数不行。这一步本来也**没有碰导出热路径**（只动了状态层和界面），记这行只是为了让序列不断。

**字节数相同不等于字节相同**——`make-sample` 生成的源素材本身就不确定（同参数两次生成大小一致、SHA-256 不同），所以导出文件的哈希永远在变，不能当回归信号。真要证"输出没变"得去哈希链路上确定的那一段，做法见 **D9**。

第二行是 **M2 动手前的对照**：文字层和关键帧会让每帧的合成成本从常数变成可变量，没有这一行就分不清后续的下降是谁造成的。M2 每个子步骤做完都用同样的配置再跑一次。

两个读这个数时要知道的前提：

- **合成素材压得极小**（11.4 MB，远低于 9.9 Mbps × 60 秒 = 75 MB）。`make-sample` 产出的是纯色背景 + 扫描条 + 帧号水印，H.264 的码率控制不会为这种内容花掉预算。真实素材会更接近码率上限，导出也会更慢一些。**但这不影响它作为对照的作用**——M2 前后跑的是同一份素材，可比性来自"同一个输入"，不来自"输入有多真实"。
- headless Chrome。硬编走的仍是 VideoToolbox（能力探测报 `avc` + `aac`），但和有界面的 Chrome 未必逐帧一致，跨行比较时看清这一列。

每帧合成成本本身另有常驻测量：PixiJS spike 的 720p × 40 帧那一组（见 §7 M1.6），改完合成层可以直接回跑对照。

### 常驻量基线（2026-07-27 起）

倍速回答"够不够快"，这一组回答"**会不会崩**"——后者才是长视频的分水岭（§8 第 1 条）。
测量落在 `export/residency.ts`，同样是"跑一次正常导出就得到一行"，不需要额外工具。

**不用浏览器的内存 API，自己数。** 两条路都堵死，而且第二条会给假的安全感：
`measureUserAgentSpecificMemory()` 要 `crossOriginIsolated`（COOP/COEP，§2 已经因为
它会打断第三方脚本而排除掉了）；`performance.memory` 只报 **JS 堆**，而导出的内存
几乎全不在 JS 堆上——`VideoSample` 持有解码画面、`OffscreenCanvas` 的后备存储、
解码器重排缓冲。一条 30 分钟的片子能把显存吃光而 `usedJSHeapSize` 几乎不动。
所以主信号是在借出/归还处各记一笔，得到的数跨浏览器一致，而且回答的正是真问题：
**常驻量随帧号增长吗？** 不增长，峰值就与片长无关。

| 日期 | 配置 | 峰值 / 出现在 | 分项 |
|---|---|---|---|
| 2026-07-27 | 1080p 60 秒 · 6 句字幕（**修缓存之前**） | 75.4 MB / 第 1535 帧 | 音频 22 · 文字 **47.5（单调涨，从不回落）** · 解码帧 5.9 |
| 2026-07-27 | 1080p 60 秒 · 18 句字幕（修之后） | 59.6 MB / 第 **321** 帧 | 音频 22 · 文字 **31.6（第 394 帧起持平）** · 解码帧 5.9 |
| 2026-07-27 | **1080p 30 分钟**（53946 帧）· 单素材 · 无字幕 | 导出循环 **665 MB** / 第 9 帧<br>混音 **1648 MB** | 混音：解码源 330 + 渲染目标 659 + 拷贝 659<br>导出：音频 PCM 659 · 解码帧 5.9 |

第一行是这套测量上线后抓到的**第一个真 bug**，见 **D13**。两行之间字幕数多了两倍，
峰值反而降了，而且峰值位置从末尾挪到了开头——**峰值出现在开头**正是"这项开销
与片长无关"的signature，只报峰值不报位置的话，两种情况长得一模一样。

**30 分钟这条线跨过去了**（2026-07-27）：53946 帧 1080p 导出成功，169.9 秒 = **10.59× 实时**，成片 281 MB，`leaked` 全 0。导出循环从第 9 帧起就**完全平**（659 → 665 → 662），65 分钟长的循环里解码帧恒定 5.9 MB——两步式取帧循环（M2 第 4 步）经受住了长跑。

**但峰值不在导出循环，在混音，而且高 2.5 倍。** 混音峰值 1648 MB，因为**三份 PCM 同时活着**：各素材的解码结果（还挂在 `AudioBufferSourceNode` 上）+ `OfflineAudioContext` 的渲染目标 + 拷给 Worker 的那一份。这一跑的素材是单声道，换成立体声源解码那份也会是 659 MB，30 分钟的峰值就是约 **1977 MB**。外推一小时：3.2–3.9 GB，**必崩**。

这个数是补了主线程那一段计量才看见的——在此之前 `ExportProgress.residency` 在 `mix` 阶段是空的（计量器每个 JS 上下文一份，混音跑在主线程）。**不补的话这次长跑会报"峰值 665 MB"，结论会完全反过来**（"还有大把余量"）。

于是 M3 的**分段混流**从"计划内"变成"该排日程"，而且现在有了明确的设计约束：要削掉的是"三份同时活着"，不只是"最终 PCM 太大"。

三项里只有**音频 PCM 随片长线性增长**（60 秒 22 MB → 30 分钟约 660 MB），
它是 M3"分段混流"要解决的那一项，M1.5 就预告过（"一小时项目的 PCM 会到 1.4GB"）。
解码帧全程恒定 2 帧驻留、`leaked` 全 0，说明 M2 第 4 步那个两步式导出循环没有留下东西。

## 5. 兼容性现状（数据日期 2026-07）

| 平台 | VideoEncoder | AAC 音频编码 | 策略 |
|---|---|---|---|
| Chrome / Edge 94+ | ✅ | ✅ | 主战场，H.264 + AAC / mp4 |
| Safari 26+（macOS / iOS） | ✅ | ✅ | 可用于生产（Safari 26 之前完全没有音频编码） |
| Firefox 130+ 桌面 | ✅ | ❌ | 降级 WebM（VP9 + Opus） |
| Linux 桌面（任意浏览器） | ✅ | ❌ | 同上 |
| Firefox Android | ❌ | ❌ | 明确提示不支持导出 |

### 落地约定

- 启动时用 `VideoEncoder.isConfigSupported()` / `AudioEncoder.isConfigSupported()` 探测，构建能力表，据此决定可用的导出格式。
- **不静默降级。** 用户点了"导出 MP4"结果拿到 WebM 是投诉源。能力表要在界面上常驻可见（见 §6）。
- H.264 硬编在部分设备不可用（无硬编且软编未启用），必须准备 VP9 / AV1 备选。
- 若引入 ffmpeg.wasm 多线程版需要 COOP/COEP 响应头（SharedArrayBuffer），会连带打断页面里的第三方脚本和跨域 iframe。这是不把它放主路径的另一个原因。

## 6. 界面设计决策

设计稿：一个应用外壳承载四种状态（剪辑台 / 素材导入 / 导出三态 / 兼容降级），不做四张独立稿——它们本来就是同一界面的不同时刻。

### 已固化的视觉规则

- **四区固定，不做浮动面板**：素材库在左、预览居中、检查器在右、时间轴横贯底部。沿用 Premiere / Resolve / 剪映共有的骨架，用户不需要重新学。
- **强调色只出现在三处**：播放头、选中片段、主操作按钮。别处一律灰调，让"当前在哪一帧、选中了什么"永远是画面里最亮的信息。
- **片段按类型着色**（视频钢青 / 音频苔绿 / 文字靛 / 图片紫灰），缩略图和波形直接画在片段里，时间轴缩到很小时仍能靠颜色和形状认出结构。
- **把技术事实做进界面**：底部状态栏常驻显示探测到的编码能力（H.264 硬编 / AAC / 显存 / 代理档位）；导出面板右侧先摊开「本机能力」再让用户选格式。客户端导出的成败取决于本机能力，用户点导出之前就该知道自己能导出什么。
- 页面框架跟随系统明暗主题，**剪辑器外壳固定深色**（真实 NLE 就该如此，是刻意选择而非遗漏）。

### 决策记录

> 格式：决定 / 理由 / 放弃了什么 / 什么情况下要重新评估

**D1 · 默认 5 轨**（2026-07-25）
文字 / 叠加 / 主视频 / 人声 / 音乐。Vlog 的常规配置一次给齐，用户不用先学"怎么加轨道"再开始剪。空轨道成本很低，缺轨道的挫败感很高。
*放弃*：新建项目只给 3 轨、按需添加。
*重新评估*：如果首屏高度成为问题（小屏笔记本），或数据显示大量用户从不使用叠加轨。

**D2 · 磁吸默认开**（2026-07-25）
新手最容易犯的错是留下 1 帧黑缝，磁吸默认开就消掉了这类事故。精细微调按住 `⌥` 临时关闭。
*重新评估*：如果收到大量"对不准"的反馈，说明磁吸阈值需要调，而不是默认值需要改。

**D3 · 缺 AAC 时禁掉 MP4，但把原因写在选项里**（2026-07-25）
无声视频不是任何人的目标，是编码能力缺失的副产品，所以不给这条路。**曾经实现过"允许 + 二次确认"并放弃**——那个确认框的推荐项永远是 WebM，说明岔路口本身不该存在；一个确认对话框的推荐选项恒定不变时，它其实是在替被禁止的方案说话。成本也不对称：允许的收益是极少数人省掉一次转码，代价是所有误点的人等几十秒拿到废文件（而且大概率忘了自己点过确认，当成 bug 报回来），外加一个模态、一套文案、一条"无声导出"分支要在后续所有导出逻辑里长期维护。
禁止的前提是**必须解释清楚**：MP4 选项就地写「这个浏览器不能编码 AAC，导出会没有声音 · 改用 WebM」，出路可点。纯置灰不解释就是黑箱。实现上不要用整体 `opacity` 压暗——那会把说明文字一起压到读不清；主标签和单选圈降级，说明文字保持完整对比度。
「仅音频」同样受影响（M4A 也需要 AAC），自动降级成 Opus，后缀跟着变 `.webm`。
*重新评估*：**接入 wasm AAC 编码器（libav.js）之后必须重新评估。** 那时岔路口的两条路各有真实代价——「快但无声」vs「慢但有声，多花 3 倍时间」——用户确实需要自己权衡，确认层才有存在意义。现在两条路里有一条是纯劣势，不构成选择。

**D4 · 预设用场景词做主标签，参数留在同一行**（2026-07-25）
```
标准发布 · 1080p · 10 Mbps      ← 默认
高清发布 · 1080p · 16 Mbps
快速分享 · 720p · 6 Mbps
存档母版 · 与源片一致
```
场景词回答"我该选哪个"，参数回答"选了会得到什么"。
*放弃*：纯参数命名（要求用户知道码率意味着什么，Vlog 用户只会默认选第一个）；用第三方平台名（发抖音 / 发 B 站）——平台规格会变、名字会过期，得长期维护一张清单，且不同人对同一平台的预期并不一致（有人要竖屏）。

**D5 · PixiJS 后端先 spike、后迁移；M2 拆成两段**（2026-07-26）

M2 四项里只有滤镜和 shader 转场必须走 GPU：文字层 Canvas2D 的 `fillText` 足够（Pixi v8 的 `Text` 内部也是先用 Canvas2D 画成纹理，中文断行和字体回退反而更好控），关键帧是纯数值插值、与渲染后端无关，交叉溶解 `globalAlpha` 就够。所以**文字 + 关键帧 + 基础转场先在 Canvas2D 上做完，把图层模型、关键帧求值、转场时间模型定死；滤镜之前再换后端**。
理由不是省事，是**风险要分开承担**：同时换渲染层和加图层类型，画面一旦不对就分不清是关键帧算错了还是纹理上传错了——三个自检能告诉你"错了"，但定位成本翻倍。
但 spike 必须**在写 M2 任何功能代码之前**做完，因为"Pixi 在 Worker 里跑不跑得起来"是个会波及接口设计的结论。已落地为 `dev/verify-pixi.ts`（前提断言，见 §7 M1.6；M2 第 2 步又往里加了图层变换的摆位比对，Safari 实测后加了 2 项上下文预算，现共 17 项）。
*放弃了什么*：一步到位换后端再开始写 M2（省一次接口适配，但把两类风险叠在一起）；用 WebGPU（Pixi v8 默认优先它——两个后端等于两套光栅化行为，同一份 EDL 在不同机器上出不同画面，导出要的是确定性）。
*重新评估*：如果 M2 前半段发现 Canvas2D 连基础转场都吃力（例如需要按像素混合的擦除），提前切；或 Pixi 的 WebGPU 后端稳定到可以证明两后端逐像素一致。

*2026-07-27 补*：Safari 26 上跑完了，前置结论成立（见 §7 M1.6）。同时改了 spike 里那条吞吐断言的**含义**——它原本问"Pixi 是不是个坏主意"，那个提法预设了有替代方案；而后半段的滤镜 / LUT / shader 转场在 Canvas2D 上做不了，所以它现在只问"是不是出了数量级的结构性错误"。Safari 的 1.69× 记成账，不当卡口。真正拦路的是新暴露出来的 **WebGL 上下文预算**：Safari 上连开 12 个合成器就会把**长命**的那个（生产里是预览）驱逐掉，第 7 项断言已经红了。这是换后端前必须先解决的唯一阻塞项，做法见 §7 M1.6。

**D6 · 文字层进自检用「分区测量」，不用「排除区域」**（2026-07-26）

三个自检现在靠"测试素材背景色相随帧号线性渐变"来断言取到的是源片第几帧，而 `measure()` 取的是画面区平均色——文字一叠上去，色相就不再精确编码帧号。

做法：给 `measure()` 加一个**可选矩形参数**，同一份测量分两块用。背景区（避开文字）继续做色相断言，现有 23 项一个字不用改；文字区做预览与导出的逐像素比对，和现在比黑边几何是同一个套路。参数加在 `measure()` 上而不是新写一个函数——「两条自检共用同一套测量」这条约定要保住，各写一个"怎么算平均色"，比对结果就不可比了。

自检素材里的"文字"用**纯色实心块**，不用真实文案：真实文案的抗锯齿边缘会让两条路径有细微差异（栅格化路径不同），容差定松了漏 bug、定紧了天天误报；纯色块边缘少、面积大，位置偏一个像素就能被抓到。真实文案的渲染质量（中文断行、字重、描边）靠截图肉眼比对，不进数值断言——两种验证混在一起两边都做不好。

*放弃了什么*：「文字限定在固定区域、measure 时排除那块」。它的硬伤是**排除了文字区就等于没验文字**，而文字恰好有几个典型的静默失效全落在那块里：预览里有导出里没有（硬规则 2 的经典形态）、两条路径位置差几像素（字体度量或 DPR 不一致）、该出现的帧没出现。它还会和 `measure()` 判黑边的逐行扫描打架。
*重新评估*：如果文字层做出来发现"位置"这个维度已被别的机制锁死（例如文字也走 `ComposeLayer` 的变换、而变换本身有单测），文字区的逐像素比对可以退化成更便宜的存在性断言。

**D7 · 预设按短边封顶，不按高度**（2026-07-26）

「1080p」在竖屏语境里指 **1080×1920**（抖音 / Reels / Shorts 都这么算），不是长边 1080。所以 `resolvePreset` 用 `min(width, height)` 封顶，横竖屏在同一预设下得到相同的像素量；档位标签里 `p` 前面的数也是短边。

*放弃了什么*：**按高度封顶**——这正是 M1.5 的原实现。它让 1080×1920 输出成 608×1080，像素量只剩三分之一，而标签上仍写着「1080p」。当时的出发点是"不要把竖屏拉成横向"，这个顾虑是对的，但**不变形**和**按长边封顶**被混成了一件事：按短边封顶同样不会变形。

这个 bug 是从一次真实导出的结果面板上看出来的（`616×1080`），不是自检抓到的——它不属于"静默产出错误的片子"那一类，成品能播、比例也对，只是分辨率悄悄低了一档。**原来的单测还把错误行为断言死了**（`expect(r.width).toBe(608)`），改对反而会让测试变红。断言写的是"当前行为"而不是"应有行为"时，测试就从护栏变成了水泥。

*重新评估*：如果出现"按总像素数封顶"的需求（例如为移动端限制解码负载），短边口径要让位——那时超宽画幅（2.39:1）的像素量会比 16:9 高出一截，短边相同但负载不同。

**D8 · 轨道只分画面/声音，"素材还是文字"由片段自己判别**（2026-07-26）

`Clip` 改成判别联合 `{kind:"media", sourceId, sourceIn} | {kind:"text", text}`，而 `TrackKind` **保持** `video | audio` 不变。默认布局里 T1 轨叫「字幕 / 标题」，那是摆放约定，不是类型约束——文字片段可以放在任意画面轨上。

两个选择各有理由：

- **用判别联合，不用"`sourceId` 可选"**。可选会把 null 处理散到每一个消费点（取帧、混音、缩略图、裁切上限、检查器共 9 处），漏一处不报错，只会在导出时静默少一层画面。判别联合让 TS 在 strict 下强制每处先表态；这次改完编译器一次点出了全部 9 处加 4 处测试夹具。
- **不加 `TrackKind: "text"`**。加了之后 `moveClip` 的"同类轨才能拖"检查会把「标题压在叠加轨上」直接禁掉，而那是常规需求（Premiere / Resolve 的 V 轨也同时装视频、图片、标题）。轨道回答"走画面还是走声音"，片段回答"这一段是什么"，两个问题分开问。

连带的两处收口：取帧三函数（`sourceMicrosAt` / `sourceCenterMicrosAt` / `toSourceFrame`）的形参收窄成 `MediaClip`，文字片段连编译期都传不进去；`visibleVideoClips` 返回**混排的联合**而不是拆成两个函数——叠加轨的素材和字幕轨的文字谁压谁是同一个 z 序问题，拆开就等于让调用方再合并一次顺序，而那个反转只允许有一处。

*放弃了什么*：**专用文字轨**（见上，会禁掉合理操作）；**`sourceId` 可选**（见上）；**给文字片段现在就定样式字段**（字体/字号/颜色/描边）——渲染器还不存在，现在定等于凭空猜形状；位置和缩放属于 `ComposeLayer` 的变换（第 2 步），不该在片段和图层两处各存一份。

*重新评估*：如果出现"某条轨必须只装文字"的真实需求（例如给字幕轨挂整轨统一样式，或做语音转字幕的批量落轨），那时再加的是**轨道级默认样式**，仍然不是类型约束。

**D9 · 图层变换相对"默认留边位置"，且恒等变换走原贴图路径**（2026-07-26）

`ComposeLayer` 加上 `LayerTransform{x, y, scaleX, scaleY, rotation, opacity}`，全部**相对 `containRect()` 算出的默认留边矩形**：位移是相对默认中心的输出像素偏移，缩放是相对默认尺寸的倍数，旋转绕图层中心。摆位计算收在 `placeLayer()` 一处，两个后端都从它取数。`containRect()` 因此从"合成器替每个图层硬算"降级成了**默认变换**——不降级，用户就没法把画中画拖到角落。

两个刻意的选择：

- **相对默认位置，不是绝对画布坐标。** 关键帧要表达的是"放大到 1.2 倍""挪到右下角"，绝对像素一换输出分辨率就全错，而同一个项目要能同时导 1080p 和 720p。代价是"铺满画布"这类需求得靠 scale 反算，但那是少数。
- **恒等变换必须走与加变换之前完全相同的 `drawImage` 调用**（`isDefaultGeometry()` 判定）。看起来是两条重复路径，实际是确定性要求：`translate(cx,cy)` 再 `drawImage(-w/2,…)` 数学上等于 `drawImage(dx,…)`，但浮点上 `(dx + w/2) - w/2` 未必精确回到 `dx`，边缘像素可能挪半个像素——而留边断言逐行判黑，半个像素就够让"上黑边高度完全相等"变成差 1px。`opacity` 不参与判定，它不改几何。

**验收方式本身值得记下来**："三个自检的像素输出一个都不能变"最初想用"导出文件的 SHA-256 前后相同"来证，但这条路是死的：`make-sample` 生成的源素材本身就不确定（同参数两次生成大小相同、字节不同，MP4 封装写了时间戳），导出哈希因此永远在变。改成**直接哈希合成出的像素**——把改动 stash 掉、用同一段脚本跑改动前的合成器，两次 `getImageData` 的 SHA-256 完全相同。教训是：**验"输出没变"要找链路上真正确定的那一段去哈希，别拿末端产物**，末端裹着时间戳和编码器状态。

*放弃了什么*：**绝对画布坐标**（见上）；**用左上角矩形表达最终摆位**——旋转必须绕中心，用左上角表达就得在两个后端各写一遍"平移到中心、转完再挪回去"，那正是 `containRect` 当初要收拢的重复；**把变换塞进 `Clip`**——同一个变换在片段和图层两处各存一份必然分叉，`Clip` 只存关键帧，求值结果只经 `ComposeLayer` 进合成层。

*重新评估*：如果要做"填充/裁切"（cover 而不是 contain）这种改变**默认**摆位的模式，那时 `containRect` 要变成可选的适配策略，`LayerTransform` 的相对基准也跟着变——届时要重新确认恒等快路径的判定条件。

**D10 · 关键帧：帧偏移相对片段、只给命名缓动、静态值与动画并存**（2026-07-26）

`anim/keyframes.ts` 是纯求值模块，`Keyframe{frame, value, easing?}` + 每个属性一条独立序列（`KeyframeChannels`），作用目标是 D9 的六个量。四个定死的选择：

- **帧偏移相对片段起点，不是绝对时间轴帧号。** 用绝对帧号的话，用户每次在时间轴上挪一下片段就得重写它全部关键帧，而挪动本来不该影响动画。代价是**裁入点时要平移关键帧**（入点右移 10 帧 = 少用开头 10 帧，偏移要减 10 才贴住原内容），这件事归到"把关键帧接进 EDL"那一步。
- **求值全程在帧号空间，秒根本进不来。** 所以这个模块连帧率都不需要知道——硬规则 1 说"禁止用浮点秒做帧运算"，最省心的落实方式是不给秒留入口。唯一的浮点是区间内的归一化进度，它是两个整数帧差的比值，喂给的是位置/缩放这类本来就连续的量，不参与任何帧定位。
- **只给命名缓动（含 `hold`），不给贝塞尔控制点。** 曲线编辑器在 §9 里是明确推后的界面，现在把控制点塞进模型等于替一个还没设计的 UI 定死数据形状。`easing` 是关键帧上的一个字段，将来加 `{kind:"bezier", …}` 不破坏现有数据。缓动归**左端**关键帧所有：一段区间只有一条曲线，挂在起点上就没有"左边说 ease-out、右边说 linear 听谁"的歧义。
- **静态值与关键帧并存，有关键帧的属性覆盖静态值。** 所有 NLE 都这样：先调出满意的值，再决定要不要让它动。强迫"打了关键帧就得删静态值"会让"临时关掉动画"变成破坏性操作。

一条隐蔽的连锁约束：**没有任何属性被动画时，`resolveTransform` 必须原样返回 `base`（包括返回 `undefined`）**。顺手返回一个 `{}` 会让所有没打关键帧的图层集体掉出 D9 的恒等快路径，画面整体挪半个像素——不报错，只是所有旧项目的成片都轻微变了。已有单测钉住。

*放弃了什么*：**绝对时间轴帧号**（见上）；**贝塞尔控制点**（见上）；**每个关键帧配进/出两条曲线**（After Effects 的做法，但那要求 UI 能编辑手柄，而手柄编辑器被推后了，两条曲线现在只会产生歧义）；**区间外线性外推**——外推让缩放冲到负数、不透明度越过 1，画面凭空翻转或消失且不报错，一律保持端点值。

*重新评估*：曲线编辑器开工时把 `easing` 扩成判别联合；如果出现"整轨统一动画"（例如整条字幕轨共用一套入场）的需求，那时要加的是轨道级默认值，不是把偏移改回绝对帧号。

**D13 · 栅格缓存按字节限流，不按条数**（2026-07-27）

文字栅格缓存原本按**条数**卡（32 条，满了整体清空）。常驻量计量一上线就抓到它：
一条 60 秒、6 句字幕的时间轴，缓存从 0 单调涨到 **47.5MB 从不回落**，里面全是
已经播过的字幕。根因是每张栅格都是**输出尺寸**的画布（D11 的选择，为了让
`containRect` 退化成 1:1），1080p 下单张 7.9MB——同样 32 条，720p 是 113MB、
**1080p 是 253MB、4K 是 1GB**。条数上限的根本问题是**它对分辨率一无所知**，
而会爆的是字节。

改成 `RasterCache`：字节预算 32MB + LRU 淘汰 + 保底留 2 张。三个选择：

- **上限用会爆的那个单位。** 32MB 在 1080p 上约 4 张、720p 上 9 张、4K 上靠下限兜底。
- **LRU，不是整体清空。** 想要的其实是"片段不再可见就淘汰"，但栅格化这一层不认识
  片段。LRU 不需要调用方配合就能逼近它：正在播的那句每帧被摸到，播过的自然沉底。
  让调用方每帧报一次可见列表会更准，但那是个**忘了调也不报错**的接口，只会静默
  退回今天这个问题。
- **保底留 2 张。** 同一帧上可能同时有字幕和标题，留不住就等于逐帧重排，那是缓存
  存在的全部意义。代价是超高分辨率下字节上限会被突破——刻意的取舍。

效果：字幕数从 6 句加到 18 句，文字缓存在第 394 帧封顶在 31.6MB 后**持平**，
峰值总常驻从 75.4MB 降到 59.6MB，且峰值位置从第 1535 帧挪到第 321 帧。

*放弃了什么*：**把栅格画得更小**（紧贴文字的包围盒 + 偏移）——那会推翻 D11 里
"画在输出尺寸的画布上、于是默认摆位天然正确"这条，合成层要重新处理文字层的摆位，
连带动到 D9 的恒等快路径判定；**调用方驱动的可见性淘汰**（见上，接口太容易忘）。

*重新评估*：如果出现"同一帧上四五个文字层"的用法（多语言字幕 + 标题 + 水印），
把保底张数提上去，并把预算改成随输出分辨率缩放而不是定值。

**D12 · 编辑入口收在纯函数里，界面只做单位换算和"改静态值还是改关键帧"的分岔**（2026-07-27）

变换 / 关键帧 / 文字的编辑操作全部落在 `state/operations.ts` 的纯函数上（`setClipTransform` / `setKeyframe` / `removeKeyframe` / `clearKeyframes` / `setTextContent` / `setTextStyle` / `addTextClip`），`ui/Inspector.tsx` 只负责渲染和换算。四个定死的选择：

- **单位换算只在 UI 层。** EDL 里旋转存弧度、缩放和不透明度存倍数、字号存"占输出高度的比例"（D9 / D11 的直接结果）。界面显示度数和百分比，换算收在 `PROPERTY_SPECS` 的 `toDisplay` / `fromDisplay` 一对函数里。散到各个输入框上迟早会出现"这个框按度算、那个框按弧度算"，而画面上只表现为"转多了"。
- **上下限与缺省值只有一份**（`TRANSFORM_RANGES`，纯函数层导出给 UI 用）。两处夹紧规则不一致时，用户看到的是"输入框允许输入、松手却弹回去"。它和 `PROPERTY_LABELS` 都按 `Record<AnimatableProperty, …>` 声明——往 `ANIMATABLE_PROPERTIES` 里加属性会**编译不过**，不会静默漏配。
- **同一个输入框，有关键帧时改的是这一帧的关键帧值，没有时改的是静态变换。** 这是 D10"静态值与动画并存"在界面上的必然形态，也是所有 NLE 的行为。于是播放头不在片段内时动画值不可编辑——那时"当前帧"没有意义，硬写会打出偏移为负的关键帧。
- **"值没变"是第三种结果，不是失败。** `EditResult` 允许 `changed:false` 且**没有** `reason`：滑块拖到边界后继续拖会一直发同一个值，一律当失败会让状态栏持续闪红字。store 的 `apply()` 据此决定要不要提示。

两个必须归一化的地方，都是为了保住 D9 / D10 的快路径：**改回缺省值时要把 `transform` 字段整个删掉**（而不是留 `{x:0}`），**删掉最后一个关键帧时要把 `keyframes` 字段整个删掉**（而不是留 `{}`）。合成器的恒等判定看的是值不是字段，所以这不是正确性问题；但它让"这个片段动过变换/有没有动画"在数据层一眼可判，UI 的重置按钮和"没用变换的输出逐像素不变"因此共用同一个依据。严格模式开了 `exactOptionalPropertyTypes`，所以清除必须真的 `delete`，不能赋 `undefined`。

*放弃了什么*：**把编辑逻辑写进组件**（和 M1 一样的理由：边界条件多到必须能脱离浏览器单测）；**给文字片段一个"位置"样式项**（位置有两个来源就必然打架，D11 已经定死由 `transform` 表达）；**负缩放做翻转**（两个后端对负尺寸的处理没验过，要开得先在 Pixi spike 里加用例，所以 `scaleX/scaleY` 夹在 `[0, 20]`）；**关掉动画时只删关键帧**（属性会跳回一个很久以前的静态值，画面突然弹走——现在 `clearKeyframes` 把播放头当前的求值结果烘进静态变换，一步撤销）。

*重新评估*：曲线编辑器或时间轴关键帧轨开工时，`setKeyframe` 要扩出"移动关键帧时间"的操作（现在只能删了重打）；那时合并键要从 `keyframe:${clipId}:${property}:${offset}` 换成带关键帧身份的键，否则拖动中偏移一变就断成多步撤销。

**D11 · 文字栅格化一次、画在输出尺寸的画布上、尺寸一律用比例**（2026-07-26）

`compose/text-raster.ts` 把一段文字画成一张图，合成层当普通 `{ kind: "image" }` 图层贴上去。三个选择：

- **栅格化只有一份，不让两个后端各画一遍。** 合成层有 Canvas2D 和 Pixi 两个后端，各自画文字就等于在硬规则 2 上开一个新入口——字形、断行、描边宽度都可能不一样，而这类差异不报错，只会让成片的字幕比预览里粗一点、断行差一个字。现在预览和导出调同一个 `rasterizeText()`、共用同一份缓存，字形一致成了结构性保证。（Pixi v8 的 `Text` 内部也是先用 Canvas2D 画成纹理，做法相同；我们要的是"两条路径共用同一份栅格结果"，所以自己来。）
- **画在输出尺寸的透明画布上，不画在紧贴文字的小图上。** 合成层给每个图层的默认摆位是 `containRect()`——等比缩放**铺满**输出。那对视频是对的，对一张小的文字位图就完全错了：一行字会被放大到糊满全屏。画在输出尺寸上，`containRect` 退化成 1:1，默认摆位天然正确，合成层一行都不用改，也就不用去动 D9 里那条恒等快路径的判定。**代价**是每个文字层一张全尺寸 RGBA 画布（1080p 约 8MB），靠缓存摊掉。
- **字号、描边、阴影全部存"占输出高度的比例"。** 绝对像素在换输出分辨率时全错——同一个项目导 1080p 和 720p，字幕不该一个正常一个巨大。与 D9 里"变换用相对量"是同一条理由。

于是**文字的位置和大小完全由 `LayerTransform` 表达**：文字在栅格里恒定居中，往下挪给 `transform.y`、放大给 `scale`。定位机制只有一套，不存在"样式里的位置"和"变换里的位置"打架。

断行是这一步唯一有真实算法的部分，第一版写错过：**逐字符判断"这里能不能断"，在拉丁词中间发现超宽时已经退不回上一个空格了**，整个词只能溢出边界。改成先切成"可断块"（宽字符各自成块、拉丁词整块、空白并入前块尾部）再逐块填行。避尾也不能只做"不在这里断"——那会让开括号卡在行中间而行照样超宽，必须**把断点前移**，把行尾的禁则字符一起挪到下一行。切分用 `Intl.Segmenter` 按**字素簇**而不是码点：码点能保住代理对，但保不住 ZWJ 合成的 emoji（👨‍👩‍👧 会散成三个人）和组合符号。

*放弃了什么*：**两个后端各写一套文字渲染**（见上）；**紧贴文字的小位图 + 给 `ComposeLayer` 加"适配模式"**——那要动合成层的几何路径，正是 D9 重新评估条款里警告的事，而收益只是省一点内存；**绝对像素字号**（见上）；**样式里带位置字段**（与变换重复，必然分叉）；**自定义 web 字体**——栅格化在主线程和 Worker 各跑一次，字体没在两边都注册就会静默回退到默认字体，那是"预览和导出不一致"的经典形态，要支持必须先把字体文件同时喂给两个上下文。

*重新评估*：如果全尺寸文字画布的内存成为问题（大量同屏文字层、或 4K 输出），再考虑"紧贴位图 + 适配模式"，但那时要连带重新确认恒等快路径的判定条件。

**D6 的落地与偏离**：D6 原本要求文字区做**逐像素比对**，理由是"两条路径的栅格化路径不同，抗锯齿边缘会有细微差异"。这个前提被上面第一条选择消掉了——栅格结果只有一份。所以按 D6 自己的重新评估条款（"位置这个维度已被别的机制锁死时可以退化成更便宜的存在性断言"），文字区的断言现在是：**两条路径都画出了文字**（区域非黑）+ **文字块的四条边完全相同**。分区测量本身照原样落地（`measure()` 加可选矩形），因为背景区仍要继续用色相编码帧号。

第一版的分区**取样区选错了**：文字放在画面区里，量到的非黑像素来自视频而不是文字，把文字整层删掉两条断言照样绿。改成把文字挪进下方留边的黑区，区域里只剩文字，断言才有牙齿——已验证去掉文字层后该区域 `maxChannel` 归 0、四条边退化成满区域。**给自检选取样区的时候要先问"这块里除了被测对象还有什么"。**

按依赖顺序推进，状态层先行（它能脱离浏览器单测，是唯一能在写 UI 之前验证正确性的部分）：

**子步骤 1 的设计要点**（已完成）

- 编辑操作（`operations.ts`）是**纯函数**：`(Timeline, 参数) → EditResult`，不碰 React 也不碰浏览器。移动、裁切、切分的边界条件极多（越界、重叠、源片用尽、至少留 1 帧、跨轨道类型不符、锁定轨道），靠手点界面验不完，纯函数才能把这些条件全部单测覆盖。
- **同轨道片段永不重叠**是核心不变量。一旦允许重叠，`compose()` 就得决定"同轨道同一帧取哪个片段"，而那个决定无论怎么定都会让用户困惑。越界操作一律夹紧或拒绝，并返回 `reason` 供 UI 提示——静默无反应比报错更难排查。
- 操作失败返回 `changed: false` 且**不进撤销栈**。否则用户会按到"什么都没发生的撤销"。
- **播放头与选中不进撤销栈**：没人希望 ⌘Z 是把光标移回去而不是撤销上一次剪辑。但撤销后要清掉指向已不存在片段的选中，否则检查器渲染空引用。

**子步骤 2 的两个坑**（已完成）

- **样式必须作用域化。** M0 面板的 `app.css` 用了 `label` / `button` / `select` 裸元素选择器，还有与编辑器同名的 `.caps` 类，全局生效后把编辑器状态栏和缩放滑块变成了纵向排列。现在 `app.css` 限定 `.m0`、`editor.css` 限定 `.ed`。**新增样式文件一律先作用域化**，不要留裸元素选择器。
- **像素与帧的换算只能有一处**（`Timeline` 的 `pxPerFrame`），位置一律由帧号乘它算出。任何地方缓存像素值再反推帧号，缩放后位置就会错乱。

**子步骤 3 的三个坑**（已完成）

- **拖拽阈值必须按二维距离判定。** 原本只看 X 位移，而跨轨道拖拽是纯垂直移动（`|dx| = 0`），永远过不了阈值，片段根本拖不到别的轨道上。只测水平拖拽是发现不了的。
- **拖拽过程只更新本地幽灵，松手才提交。** 每次 `pointermove` 都提交的话，拖到非法位置时 store 会拒绝、片段停在原地，用户看到的是"卡住了"而不是"这里不能放"。幽灵能把合法/非法画出来，且撤销栈天然只有一条记录。合法性判定复用 `operations.ts` 的纯函数（不提交、只看 `changed`），所以幽灵的规则和真正落下时执行的规则是同一套代码。
- **提交要用精确移动，不能再走一次磁吸。** 拖拽时已经算好最终位置（且要尊重 ⌥ 临时关闭磁吸），若提交走 `dragClipTo`，它会按 store 的 `snapEnabled` 再吸一次，把 ⌥ 的效果覆盖掉——实测按住 ⌥ 期望落 197，结果被吸到 200。
- 非法原因显示在**状态栏**而不是幽灵内：默认缩放下 180 帧的片段只有 75px 宽，装不下文字。

**子步骤 4 的三个坑**（已完成）

- **预览 seek 必须落在帧中点，不能是帧起点。** 帧 N 覆盖 `[N/fps, (N+1)/fps)`，seek 到恰好等于左边界时浏览器常返回**前一帧**（currentTime 精度 + "最近可解码位置"的实现差异）。表现是时间码显示 30 而画面是 `frame 29`，暂停逐帧检查时一眼可见。加半帧偏移即可。
- **素材未就绪时 seek 会静默失败**（`readyState` 为 0 时设 `currentTime` 不触发 `seeked`），结果是画一张纯黑且不报错——用户导入后立刻拖播放头就会遇到。`renderFrame` 现在先 `ensureLoaded` 再 seek。
- **播放时不能逐帧 seek**，那会卡死。做法是让 video 自己以 1× 播放、rAF 只采样当前画面，偏离时间轴超过 3 帧才纠正一次。播放头的小数部分要留在组件 ref 里，只把整数帧写进 store，否则每帧取整会让 29.97fps 的播放肉眼可见地偏慢。

**硬规则 2 有了自动护栏**：`src/dev/verify-preview.ts` 用同一份 EDL、同一帧号分别走预览和导出两条路径再逐像素比对，刻意用**方形输出**跑（16:9 素材必然产生上下黑边，黑边位置差一像素就说明缩放算法分叉）。实测两条路径的黑边均为 70px、主色调差异为 0。已接进自检面板。

**子步骤 5 的要点**（已完成）

- **代理只服务预览，导出始终读原片。** 预览走 `video.currentTime` seek，4K 源片每次 seek 都要解一整个 GOP 的高分辨率帧，拖播放头明显跟不上手；转成 720p 后成本降一个量级。代理绝不能影响成片画质。
- **代理存 OPFS 而不是内存**，且**先查缓存再转码**——重开项目不该再等一遍。命中缓存时状态直接跳到 ready。
- **转码用 mediabunny 的 `Conversion`**，不手写 decode → encode：转码只是换分辨率和码率，手写等于把导出管道的解码、背压、帧生命周期逻辑复制一份，多一处会漏 `close()` 的地方。
- **一次只转一个。** 转码吃满硬件编码器，并发只让每个都变慢，还会和导出抢编码器。
- **缩略图从代理抽帧，不碰原片**（抽 20 张 4K 帧比转一遍代理还慢），用 `samplesAtTimestamps` 一次顺序解码取多个时间点。绘制时按"这个像素位置对应源片哪一帧"反查最近的缩略图，而不是顺序平铺——裁切过的片段顺序平铺会显示错误的画面段。
- **踩过的坑**：缩略图的 effect 依赖里漏了代理状态，代理转好时片段不重跑 effect，缩略图永远不出现。代理状态要在 `TimelinePanel` 订阅后往下传。

**M1 明确没做的**：音频波形（`A1`/`A2` 片段显示纯色）。波形要解码音频算 RMS，和 M2 的音量包络是同一块工作，一起做更合理。

**M1.5 · 导出闭环** ✅ 已完成（2026-07-25）

M1 结束时导出管道只认"一个文件 + 一对帧号"，编辑器剪出来的多片段时间轴根本导不出来。这一步把它接上，顺带把首屏体积和硬规则 9 的欠账一起清掉。

| 多轨音频混流（主线程） | `src/audio/mixdown.ts` |
| 流式写盘 | `src/export/write-target.ts` |
| 导出预设 | `src/export/presets.ts`，10 项单元测试 |
| 导出面板（设置／进行中／完成） | `src/ui/ExportDialog.tsx` |
| 多片段一致性自检 | `src/dev/verify-timeline.ts`、`measure.ts` |

**为什么必须先做这一步再进 M2**

硬规则 2 当时只兑现了一半。共用 `compose()` 只保证"画法一致"，而"该画哪个片段、读源片哪一刻"是两套逻辑：预览查 EDL，导出顺序读单个文件。一致性自检也只覆盖单片段，多片段时间轴完全没有护栏。M2 的每一项（文字层、关键帧、转场、滤镜）都落在 `compose()` 里，如果导出连两个片段都渲染不出来，每个 M2 特性只能对着预览验证，导出侧攒一堆没验证过的假设，等后面再改导出时 M2 全部要重验。

**硬规则 2 的落点从"共用合成器"扩到"共用取帧决策"**

`src/edl/sampling.ts` 现在是唯一决定这三件事的地方，预览和导出都必须经过它：

1. 时间轴第 N 帧对应源片哪一刻（`sourceMicrosAt`）
2. 视频轨的绘制顺序（`videoTracksInDrawOrder`，从底到顶的反转只有一处）
3. 某帧有哪些图层可见（`visibleVideoClips`）

**顺带修掉一个静默 bug**：原来的 `toSourceFrame()` 算的是 `sourceIn + (帧 - timelineIn)`，隐含假设**源片帧率等于时间轴帧率**。导入一个 25fps 素材放到 30fps 时间轴上，时间轴走 30 帧（1 秒）会被映射成源片走 30 帧（1.2 秒），成片播放速度慢 20% 且不报任何错。正确换算要过一次时间：`sourceIn/源帧率 + (帧 - timelineIn)/时间轴帧率`，两项都算成整数微秒再相加。

**取帧游标的四条约定**（`frame-reader.ts`）

- **只能向前**。倒着问会抛错而不是静默给错帧——顺序解码是硬规则 3 的前提。
- **返回的 `VideoSample` 归 reader 所有，调用方不能 close**（硬规则 4）。时间轴帧率高于源片帧率时同一个 sample 会被连续几个输出帧复用，谁都能关就必然 use-after-close。
- **每个片段开一个新的 `samples()` 生成器**，切片段前先 `.return()` 掉旧的，否则解码器不释放，几个片段就把 WebCodecs 的配额吃满。
- **每条轨自己一份 `Input`**，哪怕两条轨用同一个源文件。Input 内部的 demuxer 有读取位置，两条轨交错拉包会互相打乱顺序。多解析一次文件头很便宜。

**音频混流必须在主线程**（硬规则 6 早就写明 `OfflineAudioContext` 在 Worker 里不可用）

用音频图而不是自己加加减减：混音本身只是相加，难的是**重采样**——素材可能 44.1k / 48k 混着来、单声道和立体声混着来，而输出只有一个采样率和声道数。把每个片段挂成 `AudioBufferSourceNode` 并 `start(时间轴位置)`，采样率转换、声道上混、叠加全由音频图完成。自己写重采样等于重新实现一遍 Web Audio 已经做对的事，且很容易在片段边界产生咔哒声。

**已知的内存边界**：整个区间一次性混完，结果是 `声道数 × 帧数 × 4` 字节，立体声 48kHz 下约 **23MB/分钟**。10 分钟约 230MB 能跑，一小时会到 1.4GB 会炸。分段混流 + 边混边喂编码器才是终解，但需要 Worker 反向向主线程请求下一段（一套请求/应答协议），归到 M3 的长视频压测一起做。

**流式写盘（硬规则 9 的欠账）**

`StreamTarget` + `FileSystemWritableFileStream` 是天然搭配：`StreamTargetChunk` 是 `{type:'write', data, position}`，正好是 `FileSystemWritableFileStream.write()` 接受的形状，MP4 回填 moov 需要的乱序写盘直接可用。picker 拿到的 `FileSystemFileHandle` 可结构化克隆，能直接 postMessage 进 Worker 由它自己 `createWritable()`。Safari / Firefox 没有 picker，回退到"流式写进 OPFS 再触发下载"——仍然是流式写盘，浏览器从磁盘喂给下载，不需要把几百 MB 读进内存。

**踩过的坑**：`output.cancel()` 会 abort 掉 writable，但**目录项还在**。取消一次就在 OPFS 留一个 0 字节文件慢慢堆积。OPFS 的条目是我们自己建的，得自己删；picker 路径不能碰，那是用户自己选的文件。

**预设：码率必须跟着实际分辨率算**

原本按设计稿把码率写死成「标准发布 = 10 Mbps」，实测 640×360 素材上翻车：分辨率被限到 360p（只降不升，放大不增加信息）后码率仍是 10 Mbps，白扔 5 倍字节换不到画质；而按公式算的「存档母版」只有 2 Mbps，四个档位直接倒挂成最低一档，三个预设的标签还都显示「360p」。改成按"每像素每帧的比特数"定档位（0.12 / 0.16 / 0.26 / 0.32），码率由实际输出尺寸和帧率算出。1080p30 下仍是约 10 / 16 / 3 / 20 Mbps，与设计稿标注的量级一致；任何源片尺寸下四档都单调递增。D4 定的是**命名**，具体数字是示意。

**多片段一致性自检**（`verify-timeline.ts`，23 项断言）

单片段比对抓不住上面这一整类错误，因为单片段时间轴根本走不到。新自检造一条 **两个片段 + 中间空档** 的时间轴（时间轴 0–60 读源片 0–60，60–80 空档，80–140 读源片 **200–260**，源片位置刻意不连续），整条导出一次，再对 7 个取样帧逐个比对。

能断言"取到的是源片第 N 帧"是因为测试素材的背景色相随帧号线性渐变（`hue = i/frames*300`），**色相编码了源片帧号**。时间轴第 80 帧应该显示源片第 200 帧（色相 200°）；如果 reader 没换游标，它会显示源片第 60 帧（60°）——差 140°，任何容差都盖不住。

实测结果：140 帧全出（空档没被跳过）、空档两条路径都是纯黑（maxChannel 0）、每个内容帧预览与导出**色相差 0°**、留边几何全部 70/70 一致、跨片段边界取到源片 200 帧（199°）。

**验收**：三个自检全绿（M0 16 项 / 单片段 5 项 / 多片段 23 项）。另外在编辑器里真剪了一条 340 帧的多片段+空档时间轴导出，读回逐帧断言：空档帧黑、帧 190 取到源片 150、末帧取到源片 299、音频混成 AAC 48kHz 立体声（单声道源片由音频图上混）。首屏主 chunk 648KB → 253KB（gzip 181 → 80KB）。

**决策：撤销栈用快照而非命令模式**（2026-07-25）

§2 原本写的是"自研 undo 栈（命令模式）"，实现时改为快照栈。
*理由*：编辑操作已经是纯函数，状态经 Immer 产出、未修改子树共享引用，"存一份完整 Timeline"的真实内存开销只有被改动的那几个节点。命令模式要为每个操作再写一遍反向逻辑，双倍代码量、双倍出错面，而它换来的内存收益在这里并不存在。
*放弃了什么*：命令模式能做"操作日志/协同编辑重放"。真要做协同再引入，届时纯函数的操作签名本身就接近命令描述，迁移成本不高。
*重新评估*：如果单个项目的 EDL 膨胀到几十 MB（大量关键帧），或要做多人协同。

**必须有合并窗口**：一次拖拽会产生几十次状态变更，不合并的话用户要按几十次 ⌘Z。按"合并键 + 时间窗口（600ms）"合并，合并键必须带对象标识（`move:${clipId}`），否则"拖 A"和"紧接着拖 B"会被错误地并成一步。撤销之后清空合并键，避免撤销后紧接的同类编辑被并进撤销前那一步。

**M1.6 · PixiJS 后端 spike** ✅ 已完成（2026-07-26）

不是功能，是 M2 的前置结论。理由与"为什么先 spike 不先迁移"见 §6 的 **D5**。落地了一个和 Canvas2D 后端可互换的 `compose/pixi-compositor.ts`（**未接进预览和导出**），和一个在 Worker 里跑的 `dev/verify-pixi.ts`（11 项前提；M2 第 2 步加了 4 项图层变换摆位比对，Safari 实测后又加了 2 项上下文预算，现共 17 项）。

实测（Chrome 150 / ANGLE Metal / Apple M3 Max，非 SwiftShader）：

| 问的问题 | 结果 |
|---|---|
| Worker 里起不起得来 | 起得来，WebGL 2.0；需要 `DOMAdapter.set(WebWorkerAdapter)`，默认的 BrowserAdapter 会去摸 `document` |
| 逐帧换 `VideoFrame` 会不会逐帧建纹理 | 不会。30 帧全程 2 个 GPU 纹理。前提是复用同一个 `ImageSource` 只换 `resource` 再 `update()`；尺寸不变时 Pixi 走 `texSubImage2D` |
| Pixi 画布交给编码器读回来对不对 | 对。留边几何与 Canvas2D **差 0px**，色相**差 0°** |
| 上下文丢失会怎样 | 默认静默变 no-op。已在合成器里装守卫，`composeFrame` 抛错 |
| 吞吐 | 1280×720×40 帧，Pixi 3.5ms/帧 vs Canvas2D 3.6ms/帧（0.97×），持平 |
| 首屏体积 | 主 chunk **不变**（252,997 B / gzip 80,027，与 spike 前逐字节一致）。Pixi 单独成 chunk：412KB raw / **gzip 119KB** |

两个只有换后端才会遇到的坑，都已经在合成器里处理掉并被断言锁住：

- **临时 `VideoFrame` 必须在 `render()` 之后才 `close()`**。纹理上传发生在 render 期间，而 Canvas2D 的 `drawImage` 是立即的——从 Canvas2D 迁过来时"画完就关"是错的，且不会报错，只会上传到一个已关闭的帧。
- **GL 上下文丢失静默出黑帧**。导出跑几分钟，切标签页、系统休眠、驱动重置都可能触发，Canvas2D 没有这个失效模式。合成器现在监听 `webglcontextlost` 并在每帧查一次 `gl.isContextLost()`（OffscreenCanvas 上事件不保证派发，所以两条都要）。

一个"量了才知道"的数：`preserveDrawingBuffer` 在这条路径上**开销为零**（151.6ms vs 151.5ms，噪声级）。画布每帧都要被编码器读走，本来就没有可保留的合成快路径。所以默认开着，把"捕获必须与渲染同 task"这条脆弱不变量买断——它一旦被破坏就是**间歇性**黑帧，不报错。

另外把 `containRect()` 从 Canvas2D 合成器里抽出来共用。两个后端各算一遍留边几何，就会在"预览 / 导出一致性自检"里差一两个像素，而那条断言要求黑边高度完全相等。

**Safari 26 实测**（2026-07-27，macOS，手动跑两轮）：**所有正确性断言全绿**——Worker 里 WebGL2 起得来、纹理 2 → 2、`preserveDrawingBuffer` 生效、上下文丢失抛错、留边 0px、色彩 0°、5 个变换用例摆位全部精确命中。**D5 要的前置结论在 Safari 上成立，可以换后端。**

两件只有 Safari 才暴露出来的事：

**① 吞吐比 Chrome 差得多，而且是真的。** 第一轮 1.60×，怀疑被上下文残留污染（当时吞吐是最后跑的，此前已建过 4 个 Pixi 上下文，控制台在报 `too many active WebGL contexts`）。把吞吐挪到**最前面**、在 0 个上下文的干净状态下重测，得到 **1.69×**——没变好，反而略高。所以这就是 Safari 的固有成本：

| | Chrome 150 | Safari 26 |
|---|---|---|
| 720p×40 帧 合成+捕获+编码 | Canvas2D 150ms / Pixi 140ms = **0.93×** | Canvas2D 158ms / Pixi 267ms = **1.69×** |
| 每帧 | Canvas2D 3.8ms / Pixi 3.5ms | Canvas2D 4.0ms / Pixi 6.7ms |
| `preserveDrawingBuffer` 开销 | ≈0%（噪声级） | **11%** · 每帧 0.68ms |

Safari 每帧多出的 2.7ms 里，`preserveDrawingBuffer` 占 0.68ms，其余约 2ms 在"WebGL 画布 → `new VideoFrame(canvas)`"这条回读路径上——Canvas2D 画布走的是另一条后备存储。**不要据此外推"Safari 导出会慢 1.69 倍"**：这一段是导出循环的大头但不是全部（还有解码、混流、封装），而且用的是纯色素材、4 Mbps。真正的 Safari 导出倍速要等后端换进去之后按 §4 的规则单独记一行。

因此把 `SLOWDOWN_LIMIT` 从 1.5× 放宽到 **2.5×**，并把那条断言的措辞从"没有倒退"改成"**没有数量级的倒退**"。理由不是为了让它变绿——1.5× 那个提法的前提是"有得选"，而滤镜 / LUT / shader 转场在 Canvas2D 上根本做不了，慢多少是要记的账不是卡口。这条线现在只抓**结构性**错误，已知的那一类是"每帧 `Texture.from()` 新建 GPU 纹理"，量级在 10× 上下；2.5 落在实测最差（1.69×）和它之间。

**② WebGL 上下文预算，而且危险的方向和直觉相反。** Safari 反复报 `There are too many active WebGL contexts on this page, the oldest context will be lost`，说明 `dispose()` 没有立刻把上下文还回去而是等 GC。Canvas2D 没有这个失效模式，是换后端**新引入**的风险。

第一版断言只测了"连开 12 个再销毁之后，**新建**的那个还画得出"——两轮都绿，但那**测反了方向**：驱逐顺序是"最老先死"，新建的天然安全。真正危险的是**长命的那个**：预览在主线程上从打开项目起就一直握着一个合成器，是全场最老的；用户每导出一次就产生一轮创建/销毁，十几次之后被判死的正是预览。补上第 7 项之后，Safari 立刻红：

> 期间一直握着的那个合成器没被驱逐（预览在生产里就是它）
> **最大通道 0 · 老的抛错：WebGL 上下文已丢失** · 新的画得出

**这是换 Pixi 后端之前必须解决的阻塞项**，也是这个 spike 到目前为止唯一真正拦住路的结论——Chrome 上 17 项全绿，只有 Safari 会这样。用户视角是"我只是导出了几次，预览怎么黑了"。合成器的守卫会抛错（不静默出黑帧，这点是对的），但预览已经不能用了。12 轮就触发，Safari 的预算相当小。

修的方向有两条，要一起做：

1. **别每次导出都新建上下文**（治因）。现在是一次导出建一个、完了销毁；Pixi 的 renderer 能 `resize()`，导出侧应当复用常驻的那一个。这直接把churn降下来。
2. **上下文丢失后能自动重建**（治果）。合成器现在只会抛错，需要一条 `recover()`：重建 renderer 与 sprite 槽位，重新上传当前帧。这条**无论如何都要做**——驱动重置、系统休眠、切标签页都会触发上下文丢失，不只是预算问题。做完要加第 18 项断言：丢了之后能自己接上继续画。

*这个结论有一处没验到*：spike 里长命的和短命的上下文**都在同一个 Worker 内**，而生产里预览在主线程、导出在 Worker。Safari 的警告说的是 "on this page"，但主线程与 Worker 是否共用同一份预算没有证据。如果不共用，预览可能实际上是安全的。**不要拿这个当免死金牌**：上面第 2 条无论如何都要做，而验证要等后端真接进去之后在 Safari 上手动跑一遍"预览开着 + 连续导出十几次"。

*仍然没验的*：iOS Safari。

**M2 · 创作能力（3–4 周）**
文字/字幕层、图片层、关键帧动画（属性曲线）、转场、滤镜/LUT、音量包络。全部实现在 `compose()` 里，天然导出一致。

按 **D5** 分两段：前半段（文字 / 关键帧 / 基础转场）留在 Canvas2D 上，把图层模型和关键帧求值定死；后半段（滤镜 / LUT / shader 转场）之前换 Pixi 后端。

前半段自己又分三步，**顺序不能换**（1 决定 2 的形状，2 决定 3 的作用目标）：

1. ✅ **`Clip` 改判别联合**（2026-07-26）。模型层能表示文字片段，取帧/混音/裁切/UI 共 9 处消费点被编译器逼着表态，字幕轨那颗"拿 `sourceId` 查不到源片"的地雷随之解除。决策见 **D8**。刻意**没做**文字渲染和"加文字"的 UI——渲染器不存在时加入口，用户只会得到一个画不出来的空片段。
2. ✅ **`ComposeLayer` 加变换**（2026-07-26）。`LayerTransform{x,y,scaleX,scaleY,rotation,opacity}`，摆位收在 `placeLayer()` 一处，两个后端都实现同一套语义，`containRect()` 降级成默认变换。决策见 **D9**。验收：三个回归自检像素输出未变（并用"哈希合成像素"证到了逐像素相同），Pixi spike 加了 4 项摆位断言，5 个用例在两个后端上都**精确命中**手算位置（0px 偏差，含 90° 旋转与画中画偏移）。
3. ✅ **关键帧求值**（2026-07-26）。`anim/keyframes.ts`，纯函数、27 项单测锁边界（区间外保持端点值不外推、端点归属、缓动方向、`hold` 跳变、同帧重复关键帧、负偏移）。决策见 **D10**。

4. ✅ **把变换与关键帧接进两条路径**（2026-07-26）。`Clip` 加 `transform` / `keyframes`（取代原来的 `effects` 占位），`visibleVideoClips` 返回**已求值**的变换，导出的逐帧循环改成两步：先把每条轨的 reader 都推进到这一帧（空档轨也要问到，否则解码器不释放、且 reader 只能向前问），再按图层顺序装配。**刻意没有和文字渲染一起做**：同时改渲染装配和加图层类型，画面不对时分不清是装配错了还是文字画错了——和 **D5** 拆 spike 与迁移是同一个理由，而变换有像素级断言可验，是更好的先行者。
   预览一致性自检加了 3 项：带关键帧的变换在 3 个取样帧上预览与导出**逐帧 0px 一致**、两条路径都**精确命中手算摆位**、以及**摆位真的逐帧在变**（变换被整条丢掉时前两条也会通过，这条兜的是"求值成常量"）。另外手动验了多视频轨导出：V2 缩到 0.4 叠在 V1 上，中心取到 V2 的色相、外圈取到 V1 的、角落是留边黑——z 序、逐层变换、"每条轨一份 Input"三件事一次验掉（`verify-timeline` 只覆盖单轨，这是它的盲区）。

5. ✅ **文字渲染 + 分区测量**（2026-07-26）。`compose/text-raster.ts` 把文字画成**输出尺寸的透明图**，两条路径调同一个函数、共用同一份缓存，所以字形一致是结构性的而非靠对齐。决策见 **D11**。断行 23 项单测（中文逐字断、拉丁词不劈开、避头尾、显式换行、字素簇），预览自检加 4 项分区断言（**D6** 落地）。

6. ✅ **编辑界面 + 还掉 D10 的债**（2026-07-27）。前五步做出来的能力此前只能靠控制台脚本注入，这一步给它们编辑入口：时间轴工具条的「T」新建文字片段（自上而下挑第一条放得下的画面轨），检查器（`ui/Inspector.tsx`）里编辑文字内容与样式、六个变换属性、以及每个属性的关键帧。决策见 **D12**。
   同时还掉 **D10** 点名的那笔债：`trimClip` 裁入点和 `splitClipAt` 的右半段现在会平移关键帧偏移（`shiftKeyframes`），落到片段外的关键帧**保留不删**——`valueAt` 在区间外取端点值，语义仍对，而且入点拖回去动画能原样回来。单测 196 → 240 项，其中 8 项专锁平移（先验证过：把两行平移代码注掉，5 项立刻红）。

**M2 前半段到此完成。** 后半段（滤镜 / LUT / shader 转场）之前要换 Pixi 后端。Safari 上的 spike 已经跑过了（2026-07-27，见 §7 M1.6）：**17 项里 16 项成立，唯一红的是 WebGL 上下文预算**——Safari 连开 12 个合成器就会驱逐最老的那个，而生产里最老的正是预览。换后端前必须先做两件事：导出侧复用常驻合成器（治因）、合成器加上下文丢失后的自动重建（治果，且不只为这一个原因）。

界面上还缺的：

- 文字层的**自定义字体**：目前只支持系统字体族，理由见 `text-raster.ts` 文件头（栅格化在主线程和 Worker 各跑一次，自定义字体要在两个上下文分别注册，否则导出静默回退到默认字体）。
- **时间轴上的关键帧轨**：现在关键帧只在检查器的属性行下面有一条迷你条（可点击跳转），没有在时间轴上按轨道展开、也不能拖动关键帧改时间。曲线编辑器仍在 §9 里推后。
- **文字阴影颜色**不可调（默认半透明黑）：`input[type=color]` 吃不了 rgba，要调得先做一个带 alpha 的取色控件。

换后端之前还有一件事要先做完：**把 `ComposeLayer` 扩成渲染后端无关的描述**（现在只有 `{kind:"sample"}` 和 `{kind:"image"}`，M2 要加文字层和变换——位置/缩放/旋转/不透明度，正是关键帧的作用目标），并在 Canvas2D 上完成。先扩接口后换后端，迁移就只是换一个实现，三个自检直接充当回归网；反过来做，接口和后端一起动，自检报错时没有基准可比。工厂函数届时要改成 `async`、返回的 `composeFrame()` 保持同步——Pixi 走动态 import，而调用点在 rAF 回调和导出逐帧循环里，每帧 await 不可接受。

## 8. 风险清单

1. **长视频内存**——最容易翻车的地方。必须分段编码 + 帧池化 + worker 隔离。**建议 M1 就开始压测，不要留到 M3。**
2. **音画同步**——根源几乎总是浮点时间戳。有理数帧号从第一天就用上。
3. **H.264 编码能力不保证**——`isConfigSupported()` 必须探测，准备好 VP9/AV1 备选。
4. **移动端**——iOS Safari 26+ 能跑，但内存上限低得多，导出分辨率要单独限制。
5. **H.264/AAC 专利**——用浏览器内置编码器不涉及自行分发编解码器；但如果为 fallback 打包 ffmpeg.wasm（GPL/LGPL + 专利池），商业发行前需要过法务。
6. **WebGL 上下文预算（Safari）**——换 Pixi 后端之后新增的失效模式，Canvas2D 没有。Safari 连开 12 个合成器就会驱逐最老的那个，而预览握着的正是最老的。**已实测复现**（2026-07-27，spike 第 7 项），换后端前必须先解决：导出复用常驻合成器 + 合成器支持上下文丢失后自动重建。后者无论如何都要做——驱动重置、系统休眠、切标签页都会触发上下文丢失。
